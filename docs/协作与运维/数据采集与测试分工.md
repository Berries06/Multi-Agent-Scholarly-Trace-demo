# 数据采集、测试自动化与人机分工技术参考

> 适用项目：研海寻踪（Multi-Agent-Scholarly-Trace-demo）
> 当前阶段：自动化实验骨架与 mock 数据已跑通，尚未开始真实数据正式评测
> 文档目的：明确需要哪些数据、哪些工作可以自动化、哪些可以交给低成本子 Agent，以及哪些环节必须由项目负责人或领域专家完成。

## 1. 核心原则

本项目的数据与评测遵守四条原则：

1. **测试集不能由被测试系统独立生成并独立评分。**
   子 Agent 可以生成候选题、候选证据和候选标签，但正式金标准必须经过人工复核。
2. **“运行次数”不等于“独立样本数”。**
   例如 100 个案例在 5 个系统、5 种扰动和 4 个随机种子下运行，可以得到 10,000 次执行，但仍然只有 100 个独立案例。
3. **有引用不等于引用正确。**
   必须检查引用文献是否存在、引用位置是否相关、证据句是否真正支持对应命题。
4. **自动化负责规模，人负责边界和真实性。**
   脚本和低成本子 Agent 负责采集、清洗、预标注、运行和汇总；项目负责人和专家负责研究边界、数据合规、最终标签和结论签字。

已实现入口为 `tests/experiments/`。它只从测试侧导入 `src/yanhai`，
包括核心消融、溯源与反证、动态学情、查询鲁棒性、工作负载扩张和端到端回归。
当前所有结果都应标记为 mock engineering run。

## 2. 你最少需要提供什么

如果希望尽快启动，项目负责人最少只需提供以下五项信息：

| 必需信息 | 示例 | 为什么需要 |
| --- | --- | --- |
| 主垂直领域 | “可信多智能体科研问答与科研训练” | 决定论文检索式、知识本体和专家范围 |
| 目标用户 | 本科生、跨学科研究生、企业技术情报人员 | 决定画像、难度和资源类型 |
| 可用模型与预算 | 仅离线模型；或允许使用某 API，每月预算上限 | 决定实验规模和对比系统 |
| 专家资源 | 2 名领域人员，每人可投入 3-5 小时 | 决定金标准是否可信 |
| 数据许可偏好 | 只收开放论文；是否允许存储公开 PDF | 决定采集和仓库保存方式 |

以下内容不是启动前的硬性要求：

- 不需要你手工下载几百篇论文；
- 不需要你手工整理所有论文元数据；
- 不需要你手工运行每一组测试；
- 不需要你从零编写测试报告；
- 不强制提供真实学生个人数据，初评可以先用合成画像；
- 不强制一开始就提供 50 组完整金标准，可以先用 20 组试标验证流程。

## 3. 所需数据总表

### 3.1 论文语料库

建议第一阶段采集 100-300 篇论文，聚焦一个可控切片，不要一开始覆盖所有学科。

每篇论文至少保存：

```text
paper_id
title
authors
year
venue
doi
arxiv_id
abstract
keywords
concepts
source_url
pdf_url
license
retrieved_at
content_hash
```

如果许可允许并且能获得全文，再增加：

```text
sections
paragraphs
sentences
references
tables
figures
evidence_spans
```

#### 可以脚本自动化的部分

- 根据检索式调用 OpenAlex、Crossref、arXiv 等公开接口；
- 获取标题、作者、摘要、年份、DOI、引用关系和开放获取地址；
- DOI、arXiv ID 和标题去重；
- 检测元数据缺失、重复论文和失效链接；
- 仅在许可明确时下载开放 PDF；
- 提取 PDF 文本、章节、参考文献和句子位置；
- 生成内容哈希和采集时间，保证可追溯；
- 输出数据来源和许可证清单。

#### 可以交给低成本子 Agent 的部分

- 为论文生成结构化中文摘要；
- 提取研究问题、方法、数据集、指标、主要结论和局限；
- 提取候选支持句和候选反证句；
- 生成论文间候选关系；
- 按“多智能体、RAG、引用、反证、个性化、知识图谱”等标签分类；
- 根据固定模板生成论文笔记；
- 标记可能需要人工重点复核的过强结论。

#### 必须由人完成或确认的部分

- 确认垂直领域和论文纳入/排除标准；
- 判断论文是否真正属于项目研究范围；
- 确认非开放数据能否保存或仅能保存链接；
- 对核心论文的关键结论和证据句进行复核；
- 对“首次提出”“显著优于”“证明”等创新性表述进行查新确认；
- 最终批准用于正式报告的论文关系。

### 3.2 论文目录与笔记

建议保存以下文件：

```text
research/
  README.md
  innovation_matrix.md
  papers/
    README.md
    catalog.csv
    catalog.json
    notes/
    pdfs/
```

论文目录字段建议包括：

```text
标题
作者
年份
会议或期刊
DOI
arXiv ID
论文页
PDF 地址
开放许可
主题标签
优先级
阅读状态
项目对应模块
项目是否已实现
实现缺口
笔记路径
人工复核状态
```

保存规则：

- 目录、链接和原创笔记可以进入 Git；
- 许可明确的开放论文可以按项目策略下载；
- 许可不明确的论文只保存链接和元数据；
- 不从绕过付费墙或授权不明的来源下载；
- PDF 较多时使用 Git LFS，或者将 `pdfs/` 保持为本地目录；
- 论文的开放许可和论文附带数据集的许可必须分别核验。

### 3.3 公共 Benchmark

建议优先考虑：

| 数据集或基准 | 用途 | 自动化程度 | 人工工作 |
| --- | --- | --- | --- |
| SciFact | 科学命题支持、反驳和证据定位 | 可自动下载、转换和运行 | 抽样核验转换是否正确 |
| QASPER | 基于完整科研论文的问题回答 | 可自动下载和转换 | 确认任务子集和语言范围 |
| ALCE 相关任务 | 引用正确性、完整性、长答案质量 | 可自动导入 | 确认指标实现与原论文一致 |
| RAGTruth | RAG 幻觉与细粒度错误 | 可自动导入 | 检查标签映射 |
| SQuAI | 科研问答、证据句和多 Agent RAG | 可自动导入公开部分 | 核对数据许可和版本 |
| AgentBench / GAIA / AgentBoard | 通用 Agent 工具、多轮和过程能力 | 可运行兼容子集 | 选择与本项目相关的任务 |

自动导入脚本应完成：

- 下载版本固定；
- 校验文件哈希；
- 保存原始许可证；
- 转换为统一 JSONL；
- 验证样本数和必填字段；
- 生成 train/dev/test 切分清单；
- 禁止将测试答案装入生成模型上下文；
- 记录使用了原始数据的哪个版本和子集。

公共 Benchmark 的作用是提供外部参照，不能替代比赛要求的本地垂直领域测试数据。

### 3.4 本地垂直领域金标准

正式版本建议不少于 60 个独立案例，初期先做 20 个试标案例。

每个案例建议包含：

```json
{
  "case_id": "LOCAL-0001",
  "profile_id": "graduate_cross_domain",
  "query": "研究问题",
  "domain": "可信科研问答",
  "difficulty": 3,
  "gold_keypoints": [],
  "gold_claims": [],
  "gold_evidence_spans": [],
  "contradicting_evidence_spans": [],
  "allowed_abstention": true,
  "expected_resource_types": [],
  "expected_learning_objectives": [],
  "source_ids": [],
  "annotators": [],
  "adjudication_status": "pending",
  "license": ""
}
```

#### 可以脚本自动化的部分

- 从论文语料中抽取候选段落；
- 按论文、主题、年份和难度分层抽样；
- 检查问题和测试语料是否重复；
- 生成标注表格或网页；
- 检查字段完整性和证据位置有效性；
- 计算标注者一致率；
- 生成待裁决分歧清单。

#### 可以交给低成本子 Agent 的部分

- 根据证据生成候选问题；
- 把长问题拆成原子命题；
- 推荐难度等级和所需背景知识；
- 预填关键知识点；
- 推荐支持、反驳或证据不足标签；
- 生成候选学习目标和资源类型；
- 发现重复案例和近似改写。

#### 必须由人完成的部分

- 判断问题是否真实、有价值且符合垂直领域；
- 最终确认每条命题的支持、反驳或证据不足标签；
- 最终确认引用证据是否蕴含命题；
- 确定题目难度和目标用户；
- 处理标注者分歧；
- 对最终测试集签字并冻结版本。

推荐标注流程：

1. 低成本子 Agent 生成候选案例；
2. 第一位专家独立标注；
3. 第二位专家独立标注；
4. 脚本计算一致率并列出分歧；
5. 第三位人员或两位专家讨论裁决；
6. 冻结 `gold-v1`，测试期间不得根据系统错误随意修改答案；
7. 如需修订，发布 `gold-v2` 并记录差异。

### 3.5 学习者画像与交互数据

第一阶段可以继续使用合成画像，但需要增加更细的知识点和任务约束。

可以自动生成：

- 不同学历、岗位和兴趣组合；
- 不同知识掌握水平；
- 不同表达偏好；
- 不同难度需求；
- 合成答题记录和边界情况。

可以由低成本子 Agent 完成：

- 将画像扩写成自然语言人物描述；
- 根据知识点生成候选测验；
- 对测验题进行格式和重复性检查；
- 生成“过难、适配、过易”的候选资源对。

必须由人完成：

- 确认画像是否符合真实用户常识；
- 如果采集真实用户数据，设计知情同意和脱敏方案；
- 确定哪些个人字段不应采集；
- 审核真实答题记录和访谈数据是否可用于比赛或论文；
- 决定真实数据保留期限和删除方式。

真实姓名、手机号、学号、邮箱、单位内部机密、未公开研究数据默认不进入测试集。

### 3.6 实验运行数据

这部分原则上可以完全自动化。

每次运行至少记录：

```text
run_id
git_commit
config_id
dataset_version
case_id
seed
model_provider
model_name
prompt_hash
retrieved_document_ids
agent_messages
claims
citations
final_output
latency_ms
input_tokens
output_tokens
estimated_cost
retry_count
error_type
metric_results
created_at
```

脚本负责：

- 展开实验矩阵；
- 并行或串行运行；
- 超时、重试和断点续跑；
- 防止同一个 `run_id` 覆盖历史结果；
- 保存每条原始输出；
- 自动计算可程序化指标；
- 生成汇总表和图表；
- 标记异常运行和缺失结果。

低成本子 Agent 可以：

- 对失败案例做初步归类；
- 汇总重复出现的错误模式；
- 从大量运行中挑选典型成功和失败案例；
- 根据固定模板生成报告草稿。

项目负责人或主 Agent必须：

- 检查实验配置是否公平；
- 确保不同系统使用相同数据和预算；
- 检查指标实现是否有循环自证；
- 完成统计检验和限制说明；
- 对报告结论负责。

## 4. 四层分工模型

### 4.1 脚本自动化层

适合规则明确、可以重复验证的工作：

- API 数据采集；
- 去重、清洗、格式转换；
- 文件哈希和许可证清单；
- Benchmark 导入；
- 数据完整性检查；
- 实验矩阵展开；
- 批量运行、重试和断点续跑；
- 确定性指标计算；
- 表格、图表和报告模板生成。

脚本的优点是便宜、稳定、可复现。只要任务能写成明确规则，应优先脚本化，不应浪费 LLM token。

### 4.2 低成本子 Agent 层

适合文本量大、允许人工抽查、结果可以被规则或专家验证的工作：

- 论文摘要和结构化笔记；
- 候选实体、关系和证据句抽取；
- 候选测试题与候选画像生成；
- 预标注和标签解释；
- 失败案例聚类；
- 报告初稿和文献综述初稿；
- 格式、语言和一致性检查。

低成本子 Agent 的输出必须保留：

- 输入文献或案例 ID；
- 证据位置；
- 使用的提示词版本；
- 模型名称；
- 置信度或“不确定”标记；
- 是否经过人工复核。

### 4.3 主 Agent / 高能力模型层

适合需要跨模块判断、研究设计和复杂推理的工作：

- 系统架构和统一数据协议；
- 指标定义；
- 对比系统公平性设计；
- 消融实验设计；
- 统计分析；
- 创新点与论文的真实映射；
- 复杂失败案例解释；
- 正式技术报告整合；
- 判断何时需要返工或补充数据。

### 4.4 项目负责人和领域专家层

以下任务不可完全委托给低成本子 Agent：

- 决定研究问题和垂直领域；
- 批准数据使用范围和许可；
- 提供或协调领域专家；
- 管理 API 密钥和预算；
- 确认真正的金标准；
- 审核真实用户数据；
- 批准“创新”“首次”“达到指标”等正式表述；
- 对比赛材料和论文署名负责；
- 最终决定是否发布、提交或公开数据。

## 5. 可直接委派的低成本子 Agent 任务卡

### S1：论文目录整理 Agent

**输入**

- 论文元数据；
- PDF 或可访问全文；
- 固定的目录字段和主题标签。

**输出**

- `catalog` 候选记录；
- 结构化论文笔记；
- 项目模块映射；
- 实现缺口；
- 待人工复核问题。

**验收**

- DOI、标题和链接与原文一致；
- 每项结论带原文位置；
- 不自行声称项目已经实现论文方法；
- 不将预印本写成正式发表论文；
- 无法确认时明确写“待核验”。

### S2：候选证据抽取 Agent

**输入**

- 已解析论文段落；
- 待验证命题；
- 允许的关系类型。

**输出**

- 支持句；
- 反证句；
- 证据不足说明；
- 论文 ID、章节和句子位置。

**验收**

- 不只返回论文标题；
- 引用范围足以让人复核；
- 区分“论文明确结论”和“Agent 推断”；
- 最终标签仍需人工确认。

### S3：Benchmark 转换检查 Agent

**输入**

- 原始 Benchmark；
- 统一 JSONL 规范；
- 转换脚本输出。

**输出**

- 字段缺失报告；
- 标签映射报告；
- 随机样本核查；
- 可疑样本列表。

**验收**

- 不改写原始金标准；
- 所有转换可追溯到原始样本 ID；
- 统计数量与原始版本一致；
- 数据许可单独记录。

### S4：本地案例预标注 Agent

**输入**

- 候选问题；
- 论文证据；
- 画像与难度规范。

**输出**

- 原子命题；
- 候选关键知识点；
- 候选难度；
- 候选支持、反驳或证据不足标签；
- 需要专家判断的问题。

**验收**

- 只能标记为“候选”；
- 不能写入冻结金标准；
- 不确定案例必须升级给专家；
- 人工复核记录不能为空。

### S5：实验执行 Agent

**输入**

- 已审核的实验配置；
- 固定数据版本；
- 固定运行脚本；
- 预算和最大运行次数。

**输出**

- 完整运行日志；
- 成功、失败和跳过数量；
- 错误类型；
- 成本和时间统计；
- 待重跑清单。

**验收**

- 不修改源码、测试集和配置；
- 不根据结果选择性删除失败运行；
- 不覆盖历史输出；
- 超预算或异常率过高时自动停止并报告。

### S6：结果汇总与报告草稿 Agent

**输入**

- 原始运行结果；
- 聚合指标；
- 统计检验结果；
- 报告模板。

**输出**

- 简报草稿；
- 完整报告草稿；
- 典型失败案例；
- 局限性列表。

**验收**

- 只能引用实际结果文件中的数字；
- 不省略不利结果；
- 区分样本数和运行次数；
- 区分工程代理指标和专家评审指标；
- 所有表格可以回溯到原始运行。

### S7：失败案例分析 Agent

**输入**

- 系统输出；
- 金标准；
- 检索证据；
- Agent 轨迹。

**输出**

- 错误分类；
- 发生阶段；
- 可能原因；
- 是否可自动恢复；
- 建议补充测试。

**验收**

- 不把猜测写成根因；
- 区分检索错、生成错、引用错、裁判错和画像适配错；
- 每类至少保留真实案例 ID；
- 高风险结论交给主 Agent 复核。

## 6. 不能交给低成本子 Agent 独立完成的任务

| 任务 | 原因 |
| --- | --- |
| 最终科学事实标签 | 容易产生自证和事实错误 |
| 论文创新性查新结论 | 需要完整检索和谨慎的学术判断 |
| 数据许可批准 | 属于法律和项目责任 |
| 真实用户知情同意 | 必须由人管理 |
| 正式比赛指标签字 | 涉及对外声明 |
| 最终论文结论 | 需要研究负责人承担责任 |
| 是否删除异常数据 | 容易造成结果选择偏差 |
| 是否达到“幻觉率 <5%” | 必须基于独立标注和正确指标 |
| 专家分歧裁决 | 不能让被测模型代替专家 |

## 7. 数据采集自动化脚本规划

正式实施时可以增加：

```text
scripts/
  data/
    collect_paper_metadata.py
    download_open_access_pdfs.py
    parse_papers.py
    deduplicate_papers.py
    validate_corpus.py
    import_public_benchmarks.py
    build_annotation_candidates.py
    generate_perturbations.py
    validate_gold_dataset.py
```

建议职责：

### `collect_paper_metadata.py`

- 输入检索式、年份、来源和数量上限；
- 从公开接口获取元数据；
- 保存原始响应和标准化记录；
- 支持增量更新；
- 不自动下载许可不明的全文。

### `download_open_access_pdfs.py`

- 只处理 `license` 和开放地址符合策略的记录；
- 校验文件类型和哈希；
- 记录失败原因；
- 不尝试绕过登录、付费墙或访问控制。

### `parse_papers.py`

- 提取章节、段落、句子和参考文献；
- 保留页码或文本位置；
- 解析失败时保留原文件并记录错误；
- 不使用解析后的文本替代原始来源。

### `import_public_benchmarks.py`

- 下载并固定公开 Benchmark 版本；
- 保存许可证；
- 转换为统一 JSONL；
- 生成字段和数量校验报告；
- 防止测试答案进入模型上下文。

### `build_annotation_candidates.py`

- 分层抽样论文与问题；
- 生成待标注案例；
- 接收子 Agent 预标注；
- 输出给专家审核的表格或界面。

### `generate_perturbations.py`

- 构造无关文献、引用错换、矛盾证据、缺失字段等压力测试；
- 每个扰动保留原始案例 ID；
- 扰动过程使用固定随机种子；
- 不覆盖原始金标准。

### `validate_gold_dataset.py`

- 检查证据位置、标签范围和字段完整性；
- 检测重复问题和数据泄漏；
- 统计标注者一致率；
- 只有人工裁决完成的案例才能进入冻结测试集。

## 8. 测试运行的自动化分工

建议对比系统：

```text
B0 当前离线规则版
B1 仅检索或抽取式基线
B2 单 Agent RAG
B3 多 Agent 多数投票
B4 提出者-批判者-裁判，无知识图谱
B5 完整博弈 + 证据图谱
B6 完整系统 + 序贯反证 + 动态学情
```

脚本负责：

- 固定数据和配置；
- 展开系统 × 案例 × 扰动 × 随机种子矩阵；
- 运行和重试；
- 保存日志；
- 计算可自动计算的指标；
- 生成统计输入表。

低成本子 Agent 负责：

- 监控长时间运行；
- 汇总失败原因；
- 抽取典型案例；
- 生成报告初稿。

主 Agent 负责：

- 确保比较公平；
- 检查数据泄漏；
- 复核指标；
- 进行消融解释；
- 组织统计结论。

人和专家负责：

- 对抽样输出做盲审；
- 对事实性、个性化和实用价值评分；
- 签署正式指标；
- 批准最终对外结论。

## 9. 测试指标的自动化边界

| 指标 | 可自动化部分 | 必须人工补充 |
| --- | --- | --- |
| Retrieval Recall@K / MRR / nDCG | 可完全脚本计算 | 核对金标准文献集合 |
| 引用存在率 | 可完全脚本计算 | 无 |
| 引用正确率 | NLI/LLM 可预评 | 专家抽样验证蕴含关系 |
| 幻觉率 | 可自动拆命题和预判 | 正式值需要独立人工标签 |
| 知识覆盖率 | 可按金标准匹配 | 语义等价边界需人工复核 |
| 难度适配 | 可计算选择准确率 | 真实学习者体验需人工或用户实验 |
| 裁判校准 | 可计算 Brier/ECE | 金标准必须可信 |
| 时延、token、成本 | 可完全自动化 | 无 |
| 协作增益 | 可自动比较消融 | 需要解释提升是否有实际意义 |
| 用户体验 | 可记录完成率和时间 | 仍需真实用户观察与访谈 |

正式幻觉率推荐定义为：

```text
不受证据支持的可验证原子命题数
--------------------------------
所有可验证原子命题数
```

不能继续使用“通过命题是否带有 evidence_ids”作为正式幻觉率。

## 11. 推荐的 10,000 次运行设计

示例：

```text
100 个独立案例
× 5 个系统配置
× 5 种证据条件（含干净数据）
× 4 个随机种子
= 10,000 次执行
```

五种证据条件可以是：

1. 干净数据；
2. 加入无关文献；
3. 错换引用；
4. 加入矛盾证据；
5. 缺失元数据或证据。

运行策略：

- 规则版和本地模型可以跑全量；
- 昂贵 API 模型先跑分层抽样；
- 初评阶段先完成 600-1,000 次可信运行；
- 系统和指标稳定后再扩到 10,000；
- 报告中把 100 写成案例数，把 10,000 写成运行次数。

## 13. 第一轮建议执行方案

在不大规模消耗 API 预算的前提下：

1. 项目负责人确认主领域和许可策略；
2. 脚本采集 100 篇开放论文元数据；
3. 低成本子 Agent 生成论文目录和结构化笔记；
4. 主 Agent 抽查并建立创新矩阵；
5. 自动导入 SciFact、QASPER、RAGTruth 等公开数据；
6. 低成本子 Agent 生成 30 个本地候选案例；
7. 专家试标并冻结其中 20 个；
8. 建立黑盒评测脚本，先测试当前规则版；
9. 根据当前失败结果决定优先实现哪个创新；
10. 扩充到 60 个金标准案例并开展正式消融。

第一轮的目标不是立即得到漂亮成绩，而是确认：

- 数据格式能否稳定；
- 标注成本是否可接受；
- 当前系统真实失败在哪里；
- 哪个创新点对指标最有贡献；
- 后续 10,000 次运行是否值得执行。

## 14. 人机分工总结

| 工作 | 脚本 | 低成本子 Agent | 主 Agent | 负责人/专家 |
| --- | --- | --- | --- | --- |
| 论文元数据采集 | 主责 | - | 设计检索式 | 定范围 |
| 开放 PDF 下载 | 主责 | - | 定策略 | 批准许可 |
| 论文摘要与目录 | 校验 | 主责 | 抽查整合 | 核心论文复核 |
| 候选证据抽取 | 校验位置 | 主责 | 复杂判断 | 最终确认 |
| 公共 Benchmark 导入 | 主责 | 转换抽查 | 指标设计 | 批准使用 |
| 候选测试集生成 | 抽样与校验 | 主责 | 设计规范 | - |
| 金标准 | 一致率统计 | 只能预标 | 组织流程 | 主责 |
| 批量实验 | 主责 | 监控和归类 | 配置与公平性 | 定预算 |
| 指标计算 | 主责 | - | 复核 | 正式值确认 |
| 报告草稿 | 表格图表 | 主责 | 整合解释 | - |
| 正式报告 | 提供数据 | 辅助 | 主责 | 最终批准 |

最终原则是：

> 脚本负责重复劳动，低成本子 Agent 负责规模化文本处理，主 Agent 负责研究设计与解释，人类负责人和专家负责真实性、合规与最终结论。
