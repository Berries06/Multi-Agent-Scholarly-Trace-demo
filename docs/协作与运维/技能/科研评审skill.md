# 科研评审 skill（验收员操作手册 A）

> 改编自 Claes Bäckman 的开源技能集 [AI-research-feedback](https://github.com/claesbackman/AI-research-feedback)（8 智能体审稿框架），并针对本项目交付物定制。
> 用途：对团队的交付物（成员工作说明、作品书、实验报告、方案文档）做投稿级评审。只读源文件，报告另存，绝不修改被评审文件。

## 八个评审视角（一次评审全部执行，合并成一份报告）

| # | 视角 | 检查什么 |
|---|---|---|
| 1 | 语言与风格 | 文笔是否流畅自然；有无模板痕迹（"照抄即可开工""结论先行""通俗版""微信发送版""手把手""适用："等词）；段落是否有水分（同一意思反复说） |
| 2 | 内部一致性 | 同一事实在不同文档里的数字是否一致（如测试项数、模型清单、日期）；交接链在双方文档中口径是否互相吻合 |
| 3 | 无支撑声明 | 交付声明与实际文件是否相符；"已完成/已同步/已提交"必须有 git/文件证据；发现夸大直接记为 major |
| 4 | 数字与指标 | 每个量化数字能否回溯到源文件（实验产物、数据文件、配置）；过期数字（旧版本数字残留）记为 major |
| 5 | 图表与表格 | 如有表格，列名与正文是否一致、数值是否可核 |
| 6 | 主审评估 | 逐条对照任务原文要求：每条要求是否被落实，落实的深度是否达到"越详细越好"（不是"提了一句"就算落实） |
| 7 | 贡献辩护者 | 站在交付者立场，找出这套交付的合理之处与已完成部分（防止误杀） |
| 8 | 贡献怀疑者 | 站在用户/评委立场攻击：哪里太简短、哪里没说清楚怎么做、哪里交接断裂、哪里读者看完仍不知道第一步干什么 |

## 深度判定规则（本项目特有，优先级最高）

1. 用户明确要求"越详细越好"时，**只检查章节是否存在=失职**；必须检查内容密度：每个任务是否给出可执行细节（命令、文件路径、验收标准、失败处理）。
2. "写到了但太简短、读者无法照做" → 该条判 FAIL，不判 PARTIAL 了事。
3. 评判以"一个此前完全不了解项目的新成员，读完能不能直接开工"为唯一用户视角。

## 输出格式

```
总判定: PASS / FAIL / PARTIAL
八个视角逐条: 结论 + 证据（文件:行号 或 命令输出）
深度打分: 每份文档 1-5 分（5=新成员可照做）
修复清单: 按优先级排序，每条写"改哪里、改成什么"
```
报告存到 `docs/协作与运维/评审报告/REVIEW_<日期>_<对象>.md`，不改原文件。
